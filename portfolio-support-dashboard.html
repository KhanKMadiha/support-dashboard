Support Ticket Analyser

Closes the loop from ticket to searchable knowledge — documentation matching, explicit gap detection, response drafting, and KB capture. Built for the same quality-ops workflow I run in enterprise support.

Open demo → View code

Enterprise support breaks down when great one-off replies never become searchable knowledge. This tool models the loop I want on every shift: ticket in → doc match or gap signal → grounded response → KB draft → publish.

Steps 1–3 run in the browser (auditable keyword matching, not a black-box triage step). Step 4 uses Claude and Notion through a Cloudflare Worker in live mode; the public GitHub Pages demo simulates publish so reviewers can try the flow without API keys or customer PII.

The four-step workflow

Step 1

From reactive triage to a closed loop

The problem enterprise support actually needs solved

Repeat tickets often mean the KB never caught up — not that the last reply was weak. This workflow makes that visible: strong match at ≥80% domain-keyword overlap, otherwise an explicit gap with related articles at 30–79%.

Design choice: Step 2 uses transparent keyword scoring (with stopwords and word boundaries), not an LLM — so you can see which terms matched and why a gap fired.

Step 2

Documentation match and gap detection

Strong match at 80%+, related articles at 30–79%

Paste a ticket, or load Sample: Strong Match (SSO) or Sample: Documentation Gap (GDPR export). Each catalogue article is scored by matched domain keywords ÷ total domain keywords, with generic support terms filtered out.

Strong match (≥80%): winning article, matched keywords, suggested response from documented steps — workflow ends at Step 3 (no duplicate KB capture).
Documentation gap (<80%): gap label plus related articles at 30–79% — interim context for the agent, then Step 4 to draft and publish new knowledge.

Thresholds were tuned on realistic enterprise tickets (SSO, API, GDPR-style gaps) so false positives like substring matches do not suggest the wrong article.

Step 3

Response drafting and KB capture

Human in the loop before anything ships

Step 3 keeps the agent in control: edit the response, copy to clipboard, original ticket visible for context. Step 4 produces a structured KB draft (title, category, summary, steps, tags) with markdown download.

In live mode, Claude drafts the article and a Worker publishes to a sandbox Notion database. On GitHub Pages, steps 1–3 are real; publish is simulated — safe default for public review (?live=1 for full stack).

Step 4

Architecture and security

Static app + Worker proxy

Vanilla HTML/CSS/JS on GitHub Pages. API keys stay on a Cloudflare Worker (Anthropic + Notion via Wrangler secrets). Open source with a README that explains demo vs live behaviour and privacy expectations.
